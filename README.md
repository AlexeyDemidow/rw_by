# 🚂 rw_by — расписание поездов pass.rw.by: API, Telegram-бот и рассылки

Проект состоит из трёх частей:

- **backend** — асинхронный сервис на FastAPI: по маршруту и дате запрашивает страницу поиска на [pass.rw.by](https://pass.rw.by) (Белорусская железная дорога), разбирает список поездов и отдаёт типизированный JSON.
- **tg_bot** — Telegram-бот на aiogram 3: выбор даты и станций (основные кнопками, остальные поиском по названию), мгновенный запрос расписания и оформление подписок с выбором интервала. К бэкенду обращается по HTTP.
- **celery_app** — периодические рассылки: Celery beat каждую минуту запускает задачу, которая находит подписки с наступившим временем и присылает расписание в Telegram.

## 📌 Статус

Ранняя стадия разработки.

Работает:

- **backend** — REST-эндпоинт `/trains`, ретраи, валидация параметров и ответов, обработка ошибок;
- **tg_bot** — выбор даты в календаре, выбор станций отправления и прибытия (6 основных станций кнопками и поиск по названию среди 105 станций), вывод списка поездов с вагонами, ценами и местами, ссылка на покупку билета, подписки на маршрут с выбором интервала рассылки, их просмотр и отмена (`/subscriptions`), уведомления администратора о запуске и остановке;
- **celery_app** — периодическая рассылка расписания по подпискам (Celery beat + worker, Redis). У каждой подписки свой интервал: от 15 минут до 12 часов (см. [Подписки и рассылка](#-подписки-и-рассылка)).

В планах: рассылка только при изменениях, кэш, тесты, Docker (см. [Планы](#-планы)).

## ✨ Возможности бэкенда

- Асинхронные запросы через `httpx` с одним общим клиентом на приложение (создаётся в `lifespan`)
- Повторные попытки с экспоненциальной задержкой и jitter при сетевых ошибках, 5xx и 429
- Парсинг HTML (`BeautifulSoup4`) и разбор строк поездов регулярными выражениями
- Pydantic-модели ответа: контракт API виден в OpenAPI (`/docs`)
- Валидация параметров на уровне FastAPI (пропущенный параметр или неверная дата → `422`)
- Различие ошибок: неверный маршрут → `404`, сайт недоступен или изменилась вёрстка → `502`

## 🤖 Telegram-бот

Бот ходит за данными в бэкенд по HTTP (`GET /trains`) и сам сайт pass.rw.by не трогает.

**Сценарий:**

1. `/start` — бот показывает календарь ([aiogram-calendar](https://pypi.org/project/aiogram-calendar/)). Доступны даты от сегодняшней до +30 дней.
2. После выбора даты бот предлагает станцию отправления, затем станцию прибытия. На экране шесть основных станций (Минск, Брест, Гомель, Могилев, Гродно, Витебск) и кнопка **«🔎 Найти другую станцию»**. На втором шаге станция отправления из списка исключается.
3. **Поиск станции.** После нажатия на кнопку поиска бот просит ввести название или его часть, например «полоц». Поиск идёт по всем 105 станциям, не зависит от регистра и считает «е» и «ё» одной буквой. Сначала показываются станции, названия которых начинаются с запроса, затем те, что его содержат. Запрос должен быть не короче двух символов. Бот показывает до 10 совпадений кнопками, а если их больше, просит уточнить запрос. Кнопка «◀️ К основным станциям» возвращает к исходному списку.
4. После выбора маршрута доступны два действия:
   - **⚡ Показать сейчас** — бот запрашивает поезда у бэкенда и присылает список: номер и тип поезда, станции, время отправления и прибытия, длительность, дни курсирования, типы вагонов с ценами и количеством мест, бейджи («Самый быстрый», «Самый недорогой») и ссылку на покупку билета на pass.rw.by;
   - **🔔 Присылать регулярно** — бот спрашивает интервал (15 мин, 30 мин, 1 час, 3 часа, 6 часов, 12 часов) и оформляет подписку на выбранный маршрут и дату (см. [Подписки и рассылка](#-подписки-и-рассылка)).
5. После мгновенного ответа предлагаются кнопки «Другой маршрут» (дата сохраняется) и «Другая дата и маршрут».

Сообщения форматируются в HTML (`escape` для всех значений из ответа). Длинный список режется на несколько сообщений до 3500 символов каждое. Если бэкенд недоступен (сетевая ошибка, таймаут 30 с или ответ 4xx/5xx), бот отвечает «⚠️ Сервер временно недоступен».

**Команды:**

| Команда          | Описание                                                                     |
|------------------|------------------------------------------------------------------------------|
| `/start`         | Начать работу: выбор даты, станций и действия                                |
| `/subscriptions` | Список подписок с интервалами; нажатие на подписку отменяет её               |

**Администратор** (`ADMIN_ID`) получает сообщения «Бот запущен» и «Бот остановлен».

**Ограничения текущей версии:**

- список станций зашит в код (`tg_bot/keyboards/keyboards.py`), а кнопки хранят не названия, а индексы станций в отсортированном списке. Если добавить или удалить станцию, кнопки в уже отправленных сообщениях укажут на другие станции, поэтому после такого обновления нужно начинать заново с `/start`;
- выбранные дата и маршрут и режим поиска хранятся в FSM-хранилище в памяти, поэтому после перезапуска бота нужно снова вызвать `/start`; сами подписки при этом сохраняются (они лежат в SQLite);
- ошибки бэкенда не различаются: `404`, `422` и `502` показываются одним сообщением.

## 🔔 Подписки и рассылка

Подписка — это связка «чат + станция отправления + станция прибытия + дата поездки + интервал рассылки».

**Как это работает:**

1. После нажатия «🔔 Присылать регулярно» и выбора интервала бот сохраняет подписку в SQLite (`subscriptions.db` в корне проекта). Одинаковые подписки одного чата не дублируются: если подписаться на тот же маршрут и дату ещё раз, у существующей подписки меняется интервал, а следующая отправка переносится на новый интервал от текущего момента.
2. **Celery beat** каждые `TICK_SECONDS` (60) секунд ставит в очередь (Redis) задачу `celery_app.tasks.send_subscriptions`. Это частота проверки, а не рассылки: большинство запусков заканчиваются сразу, потому что ни у одной подписки время ещё не подошло.
3. **Celery worker** выполняет задачу:
   - удаляет подписки, у которых дата поездки уже прошла;
   - забирает подписки, которым пора слать (`next_run_at` наступил или ещё не задан, как у новой подписки) и в той же транзакции сдвигает им следующую отправку на их интервал. Это защищает от двойной отправки, если запуски задачи наложатся;
   - группирует забранные подписки по маршруту `(откуда, куда, дата)`: на один маршрут уходит **один** запрос к бэкенду, сколько бы человек ни подписалось;
   - между запросами к разным маршрутам делает паузу 1–3 секунды, чтобы не нагружать сайт;
   - отправляет каждому подписчику расписание с заголовком маршрута;
   - если пользователь заблокировал бота, все его подписки удаляются;
   - если бэкенд недоступен, отправка откладывается на `RETRY_DELAY_MIN` (5) минут, а не ждёт целый интервал.
4. Первое сообщение по новой подписке приходит при ближайшей проверке, то есть в течение минуты. Следующие приходят с выбранным интервалом, с погрешностью до одного тика.
5. Отменить подписку можно командой `/subscriptions`: каждая подписка показывается кнопкой вида «❌ Минск → Гомель, 12.10 · 30 мин», нажатие удаляет её.

**Настройки** лежат в `tg_bot/service/subscriptions.py`:

| Константа          | Значение по умолчанию | Описание                                                          |
|--------------------|-----------------------|-------------------------------------------------------------------|
| `TICK_SECONDS`     | `60`                  | Как часто beat проверяет, у кого подошло время (используется в `celery_app/app.py`) |
| `RETRY_DELAY_MIN`  | `5`                   | Через сколько минут повторить, если бэкенд был недоступен         |
| `INTERVAL_CHOICES` | 15, 30, 60, 180, 360, 720 минут | Варианты интервала, которые видит пользователь          |

Время в базе хранится в UTC. Если БД создана более ранней версией проекта (без интервалов), колонки `interval_min` и `next_run_at` добавляются автоматически при запуске бота или первой задачи, а существующие подписки получают интервал 60 минут. Для отладки в `INTERVAL_CHOICES` можно временно добавить короткий пункт, например `(1, "1 мин (тест)")`.

> ℹ️ Рассылка присылает полное расписание на каждом цикле, а не только изменения. Отправка только при появлении мест или смене цены — в [планах](#-планы).
>
> ℹ️ Объединение запросов по маршруту работает среди подписок, у которых время подошло на одном тике. Подписки на один маршрут с разными интервалами делают отдельные запросы.

## 🛠 Стек

- Python 3.10+
- **Backend:** FastAPI + Uvicorn, httpx, BeautifulSoup4, fake-useragent, Pydantic v2 + pydantic-settings

## 🔧 Конфигурация

Скопируйте `.env.example` в `.env` в корне проекта и заполните. Файл читают все части, каждая берёт только свои переменные. Все переменные обязательные: бот и Celery не запустятся без `REDIS_URL`.

| Переменная    | Кто использует        | Описание                                           |
|---------------|-----------------------|----------------------------------------------------|
| `BASE`        | backend               | Базовый URL сайта, `https://pass.rw.by`            |
| `URL`         | backend               | Путь страницы поиска, `/ru/route`                  |
| `BOT_TOKEN`   | tg_bot, celery_app    | Токен бота от [@BotFather](https://t.me/BotFather) |
| `ADMIN_ID`    | tg_bot                | Telegram ID администратора                         |
| `BACKEND_URL` | tg_bot, celery_app    | Адрес бэкенда, например `http://localhost:8000`    |
| `REDIS_URL`   | tg_bot, celery_app    | Брокер Celery, например `redis://localhost:6379/0` |

> ⚠️ Файл `.env` содержит токен бота. Он должен быть в `.gitignore`. Если токен попал в публичный репозиторий, логи или чат, перевыпустите его командой `/revoke` у BotFather.
>
> Также добавьте в `.gitignore` файлы, которые создаются при работе: `subscriptions.db` и `celerybeat-schedule*`.

## ▶️ Запуск

Нужны Redis и четыре процесса, каждый в своём терминале и из корня проекта.

**1. Бэкенд:**

```bash
uvicorn backend.app.main:app --reload --reload-dir backend
```

Документация API: `http://127.0.0.1:8000/docs`.

**2. Бот:**

```bash
python -m tg_bot.bot
```

Перед этим убедитесь, что бэкенд запущен и администратор хотя бы раз написал боту `/start`: иначе Telegram не даст отправить сообщение о запуске. После старта откройте бота в Telegram и отправьте `/start`.

**3. Celery worker** (выполняет задачи):

```bash
celery -A celery_app.app worker -l info
```

В `celery_app/app.py` задан `worker_pool="solo"`, потому что стандартный пул `prefork` на Windows не работает. На Linux и в Docker эту настройку можно убрать.

**4. Celery beat** (запускает задачи по расписанию):

```bash
celery -A celery_app.app beat -l info
```

Запускайте **ровно один beat**: несколько экземпляров будут ставить дубли задач, и рассылки задвоятся. Воркеров может быть сколько угодно. Если вы меняли расписание в `celery_app/app.py` или `TICK_SECONDS`, остановите beat, удалите файлы `celerybeat-schedule*` в корне проекта и запустите его снова.

**Проверка рассылки без ожидания расписания:**

```bash
celery -A celery_app.app call celery_app.tasks.send_subscriptions
```

Для этого сначала оформите подписку в боте. Задача отправит только подписки, у которых время рассылки уже наступило. Если в очереди остались сообщения от удалённых задач, очистите её командой `celery -A celery_app.app purge`.

## 🔌 API

### `GET /trains`

| Параметр      | Тип                 | Описание                |
|---------------|---------------------|-------------------------|
| `dep_station` | string              | Станция отправления     |
| `arr_station` | string              | Станция прибытия        |
| `trip_date`   | date (`YYYY-MM-DD`) | Дата поездки            |

Все параметры обязательные.
Пример запроса:

```bash
curl -X 'GET' \
  'http://127.0.0.1:8000/trains?dep_station=...&arr_station=...&trip_date=....-..-..' \
  -H 'accept: */*'
```

Пример ответа (значения условные):

```json
{
  "trains": [
    {
      "train_type": "...",
      "train_number": "...",
      "from_station": "...",
      "to_station": "...",
      "dep_time": "...",
      "dep_station": "...",
      "arr_time": "...",
      "arr_station": "...",
      "duration": ".. ч .. мин",
      "days": "..., ежедневно",
      "badges": [],
      "carriages": [
        {
          "type": "...",
          "options": [
            {
              "seats": 999,
              "price": "..."
            }
          ]
        },
        {
          "type": "...",
          "options": [
            {
              "seats": 99,
              "price": "..."
            }
          ]
        }
      ]
    },
    {"...": "..."}
  ],
  "order_url": "https://pass.rw.by/ru/route?from=...&to=...&date=....-..-.."
}
```

`price` сериализуется строкой (тип `Decimal` в Pydantic v2). `order_url` — ссылка на страницу поиска на pass.rw.by для оформления билета.

### Коды ответов

| Код   | Когда                                                                 |
|-------|-----------------------------------------------------------------------|
| `200` | Запрос выполнен (список `trains` может быть пустым — поездов нет)     |
| `404` | Сайт ответил 400/404, как правило неверная станция                    |
| `422` | Некорректные параметры запроса (например, формат даты)                |
| `502` | pass.rw.by недоступен, исчерпаны попытки или изменилась вёрстка       |

## ⚠️ Замечание

Проект не связан с Белорусской железной дорогой. Данные берутся с публичной страницы сайта, поэтому формат ответа зависит от его вёрстки. Не отправляйте слишком частые запросы, чтобы не создавать лишнюю нагрузку на сайт: минимальный интервал подписки в боте — 15 минут, а очень короткие интервалы (например, тестовые) подходят только для отладки.
